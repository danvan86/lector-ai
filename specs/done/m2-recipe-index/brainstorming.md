# M2 – Recipe index and OpenRewrite run · Brainstorming

Milestone: [M2 in features.md](../../../docs/features.md#m2--recipe-index-and-openrewrite-run-) · Status: **Closed** (all questions decided)

**How to answer:** the recommended option is preselected with `[x]`. Move the `x` to choose another one. Write anything else under **Notes**.

## Already fixed by the project docs and earlier milestones

- No LLM picks recipes. The index comes from recipe metadata: `(ecosystem, package, target version) → recipe` (concept section 4, rule 2).
- Pick the most specific recipe that covers the change without overshooting the target version.
- The recipe is optional. No match → go straight to verify.
- Maven: run the recipe through the Maven plugin with CLI coordinates, no `pom.xml` edits.
- `recipeRunner` is an optional capability of the `EcosystemAdapter`. M2 adds it to the port (M1 spec, section 2).
- `RecipeIndex` is a port in `core`, implemented in the `recipes` module.
- `DependencyChange` has `ecosystem, package, fromVersion, toVersion, updateType` and is introduced in M2.
- From M1: Maven runs as a process (`./mvnw` if present, else `mvn`), `--maven-settings`, `--base`, `JAVA_HOME` as is, text report plus `--format json`, kotlinx.serialization, exit codes `0`/`1`/`2`, and tagged integration tests with real Maven.
- From M0: this repository's dependencies are updated by Dependabot. Versions live in `gradle/libs.versions.toml`.

```
lector migrate <repo> --package g:a --from X --to Y [--base <ref>]
   │
   ▼
RecipeIndex.find(DependencyChange) ──none──────────────────────┐
   │ recipe + alternatives                                     │
   ▼                                                           │
adapter.recipeRunner.run(recipe)  (rewrite-maven-plugin)       │
   │ ok → changes stay in the working tree                     │
   │ fails → reset, note it ───────────────────────────────────┤
   ▼                                                           ▼
verify (M1) ──▶ report: recipe section + Verification ──▶ exit 0 / 1 / 2
```

## Round 1

### Q1 · When and where the index is built

The biggest decision for M2.

```
A/B: build time of our tool                   C: run time
───────────────────────────                   ───────────
Dependabot bumps rewrite-recipe-bom           each pipeline run:
   │                                             │
   ▼                                             ▼
Gradle task loads all recipes,                resolve recipe JARs (network),
writes recipe-index.json                      load them in an isolated classloader,
   │                                          build the index in memory
   ▼
shipped inside our distribution
```

- [x] **A · Build time, generated by the Gradle build (not committed)** — *recommended.* A task in `recipes` loads the BOM's recipes with `Environment.builder().scanRuntimeClasspath()` and writes the index as a resource. The runtime never loads OpenRewrite and needs no network for the index. "Rebuild when the BOM is updated" happens by itself: Dependabot bumps the BOM, CI rebuilds. No file can go stale.
- [ ] **B · Build time, committed to the repo, regenerated by a task, checked in CI** — Same runtime behaviour as A. A BOM bump shows up as a reviewable index diff in the Dependabot PR. Costs a "regenerate and commit" step and a CI check that the file is current.
- [ ] **C · Run time, from configurable recipe artifacts** — Users can bring their own recipe BOM or internal recipes. Costs network, startup time, and classloader isolation.
- [ ] **D · Run time via `mvn rewrite:discover`** — No OpenRewrite in our code, but its output is human text, not structured metadata.

**Notes:** No internal recipes needed (answered in chat). → A

### Q2 · Which recipe modules are included (license)

`rewrite-spring` is under the **Moderne Source Available License** (MSAL). As far as I can tell, MSAL lets an organisation apply the recipes to its own code, but not put them into a commercial product or resell them. The M2 "done when" needs the Spring Boot recipes. I'm not a lawyer, and I'm not sure whether an index built from MSAL metadata counts as "putting them into a product".

- [x] **A · Index the full `rewrite-recipe-bom`. Never ship recipe JARs: the user's Maven fetches them at run time. Record the license per recipe and generate a license report** — *recommended.* M2 can reach its goal. The user's pipeline applies MSAL recipes to the user's own code, which MSAL allows. A legal check becomes a blocking item before the first release (M5).
- [ ] **B · Apache 2.0 modules only** — Legally simplest, but excludes the Spring recipes, so the M2 fixture would need another upgrade that has an Apache-licensed recipe (I haven't confirmed which ones exist).
- [ ] **C · Full index, but MSAL recipes only run with an explicit opt-in (`--allow-license msal`)** — The user accepts the license knowingly. One more flag, and the default run finds no Spring recipe.

**Notes:** lector-ai's commercial use is not decided yet. Legal check of MSAL before M5 (answered in chat). → A

### Q3 · Which recipe leaves the index reads

Composite recipes like `UpgradeSpringBoot_3_4` contain typed leaves, e.g. `UpgradeDependencyVersion(org.springframework.boot, *, 3.4.x)`, `UpgradeParentVersion(…spring-boot-starter-parent, 3.4.x)`, `UpgradePluginVersion(…spring-boot-maven-plugin, 3.4.x)`.

- [x] **A · Version-upgrade leaves: `UpgradeDependencyVersion` (both the `maven` and `java.dependencies` variants), `UpgradeParentVersion`, `UpgradePluginVersion`** — *recommended.* Covers what Renovate and Dependabot bump in a Maven project: dependencies, parents, plugins. Glob artifact IDs (`*`) are kept as patterns.
- [ ] **B · A, plus coordinate changes (`ChangeDependency`, `ChangeParentPom`)** — Also finds recipes for relocated artifacts (new group or artifact ID). Update PRs rarely relocate, and the matching rules get harder.
- [ ] **C · Only `UpgradeParentVersion`** — Enough for the Spring Boot fixture, too narrow for anything else.

**Notes:** A

### Q4 · Version selectors and version comparison

Leaves don't hold plain versions but selectors: `3.4.x`, `latest.release`, `latest.patch`, ranges. "Doesn't overshoot" means the leaf's selector must contain `toVersion`, and versions must be ordered the Maven way (`3.2.0-RC1 < 3.2.0`).

- [x] **A · Understand exact versions and X-ranges (`3.4.x`, `3.x`). Skip leaves with any other selector and count them in the index report. Order versions with Maven's `ComparableVersion` (`maven-artifact`). Lives in `recipes`** — *recommended.* X-ranges are what the upgrade recipes use. `latest.*` is unbounded, so it would overshoot by definition. `ComparableVersion` is Maven's own ordering, in a small artifact. A `VersionScheme` per ecosystem is extracted when a second ecosystem needs one.
- [ ] **B · All OpenRewrite selectors** — More leaves indexed, but we'd reimplement OpenRewrite's selector logic, or need OpenRewrite at run time.
- [ ] **C · A, but provide `VersionScheme` through the `EcosystemAdapter` now** — Clean per rule 1, but an abstraction with one implementation.

**Notes:** A, but we need to make sure that an old PR does not lead to downgrading from a more up-to-date version to the old version in the PR. → Round 2 (Q15, Q16)

### Q5 · Ranking when several recipes match

For `spring-boot-starter-parent 3.3.5 → 3.4.1`, several recipes may match: `UpgradeSpringBoot_3_4` (leaf directly in its list), a Spring Cloud recipe that includes `UpgradeSpringBoot_3_4`, maybe a `3.x` "best practices" recipe.

A recipe's target for a package is its **highest** leaf for that package, across the whole tree. That way `UpgradeSpringBoot_3_4`, which transitively includes the 3.3 and 3.2 recipes, never matches a change to 3.3.

- [x] **A · Rank by: tightest selector that contains `toVersion` (`3.4.x` beats `3.x`), then shallowest leaf (direct child beats nested), then recipe name. Log and report the alternatives** — *recommended.* Deterministic and explainable. The shallowest-leaf rule prefers the recipe that is *about* the package over one that only includes it.
- [ ] **B · As A, but run no recipe when the first two criteria tie, and report the ambiguity** — Safest, but loses the recipe benefit in cases where we have one.
- [ ] **C · Only consider recipes whose own (direct) list contains the leaf** — Simpler matching, but misses recipes that delegate through one level.

**Notes:** A

### Q6 · What `ecosystem` means in `DependencyChange` and the index

Gradle projects (M7) use the same Maven coordinates. Dependabot reports `maven` or `gradle`.

- [x] **A · The package namespace: `maven` for every JVM build, later `npm`, `pypi`, …** — *recommended.* One index entry per package, no matter which build tool. The build tool is the ecosystem adapter's business. Source adapters map Dependabot's `gradle` to `maven`.
- [ ] **B · The build tool: `maven`, `gradle`** — Matches Dependabot's naming, but every JVM recipe is indexed twice.

**Notes:** A, but we should not focus too much on the Java side. We need to make it generic for Python etc. → Round 2 (Q17)

### Q7 · How the recipe is executed

- [x] **A · `rewrite-maven-plugin` via CLI coordinates, goal `runNoFork`** — *recommended.* `mvn -B <plugin>:<pinned>:runNoFork -Drewrite.recipeArtifactCoordinates=<module from the index> -Drewrite.activeRecipes=<recipe>`. Plugin version pinned in the version catalog, bumped by Dependabot together with the BOM. The plain `run` goal forks the Maven lifecycle, and I expect that to compile the project first, which fails exactly when the update broke compilation. `runNoFork` should avoid that. To be confirmed with the fixture.
- [ ] **B · OpenRewrite in-process (we parse the LSTs)** — Full control, but we'd resolve the project's classpath ourselves. Much more code.
- [ ] **C · Moderne CLI** — Fast, but adds a licensing dependency on Moderne.

**Notes:** A

### Q8 · Which state the recipe runs on

The PR head already has the new version in `pom.xml`. OpenRewrite matches many changes by type. When a class from the old version no longer exists on the new classpath, its type is unknown and type-based steps may not match. Moderne recommends running migration recipes *before* the bump. I'm not sure how much this matters in practice.

```
A: head as is                       B: head, with base's manifests during the run
──────────────                      ─────────────────────────────────────────────
pom.xml = new version               pom.xml = old version (from base)
classpath = new                     classpath = old → full type info
recipe migrates what it can match   recipe bumps the version itself and migrates
                                    keep the recipe's pom.xml afterwards
```

- [x] **A · Run on the PR head as it is** — *recommended* for M2. Simplest, no ecosystem-specific file juggling. The M2 fixture includes a type-based migration, so we see right away whether it gets missed. If it does, B becomes a Round 2 question.
- [ ] **B · Run on the head, with the manifests reset to the base commit during the run** — Full type information. The recipe does the version bump itself, which may pick a different patch than the PR. The adapter has to know which files are manifests (close to `manifestDiff` from M8).
- [ ] **C · Run on a worktree of the base commit, then carry the diff over to head** — Cleanest type information, but the `pom.xml` hunks conflict with the PR's bump.

**Notes:** A

### Q9 · The recipe changes more than the PR

A Spring Boot recipe also upgrades Spring Framework, springdoc, and other dependencies. With `3.4.x` it may also move Spring Boot itself to a newer patch than the PR (`3.4.1` → `3.4.5`).

- [x] **A · Accept it, and list every version change in the report, including the PR's own package if it moved** — *recommended.* That's how the recipes are meant to work, and a Boot upgrade without its managed dependencies is often broken anyway. The reviewer sees every change.
- [ ] **B · Reject the recipe if it changes versions beyond the PR** — Strictly in scope, but throws away most of the value of framework recipes.
- [ ] **C · Accept, but revert extra version changes** — Tries to have both, and often produces an inconsistent build.

**Notes:** A

### Q10 · Working tree and capturing the recipe's changes

- [x] **A · Require a clean working tree (exit `2` otherwise). Run in place. Capture the changes with Git (modified and new files). Leave them uncommitted** — *recommended.* Language-neutral, and the diff becomes the recipe commit in M5. A clean start means "reset" can never destroy someone's work. Committing is M5's job (Git output).
- [ ] **B · As A, but commit the recipe result locally with a fixed message** — Prepares M5, but makes Git authoring decisions (author, message) before they are discussed.
- [ ] **C · `rewrite:dryRun` and read `rewrite.patch`** — No working-tree change until applied, but Maven-specific and needs a second step.

**Notes:** A

### Q11 · The recipe fails or makes things worse

- [x] **A · A failed run counts as "no recipe": reset the working tree, note it in the report, continue with verify. A successful run is always kept** — *recommended.* The recipe is a quality boost, not a prerequisite (concept section 4). Error counts before and after a recipe aren't comparable anyway: one root error can hide hundreds of others.
- [ ] **B · As A, but also verify without the recipe and keep the result with fewer diagnostics caused by the update** — Protects against a bad recipe, but doubles the build time on every run, and the counts are misleading.
- [ ] **C · Fail the whole run** — Clear signal, but blocks the fix loop for an optional step.

**Notes:** A

### Q12 · Where the `DependencyChange` comes from in M2

Source adapters only arrive in M5.

- [x] **A · CLI options: `--package group:artifact --from 3.3.5 --to 3.4.1`. `ecosystem` comes from the detected adapter, `updateType` is computed from the versions. One change per run** — *recommended.* Explicit and easy in tests. Stays useful for the benchmark (M6). Grouped updates arrive with the source adapters.
- [ ] **B · Detect it from the Git diff of `pom.xml`** — That's the fallback adapter from M8, pulled forward.
- [ ] **C · Read a JSON file with `DependencyChange[]`** — Good for grouped updates, clunky for a single change.

**Notes:** A

### Q13 · CLI shape

- [x] **A · `verify` stays. New `migrate <repo>` = find recipe + run it + verify, same options and exit codes as `verify`. The report gets a recipe section: chosen recipe, alternatives, changed files, version changes, or why no recipe ran** — *recommended.* Each command maps to one pipeline stage. `heal` (M3) adds the fix loop on top.
- [ ] **B · A, plus `lector recipes find --package … --to …`** — Handy for debugging the index without running Maven. One more command to maintain; unit tests cover the selection anyway.
- [ ] **C · One command `run <repo>` with flags to skip stages** — Fewer commands, more flag combinations to test.

**Notes:** A

### Q14 · Fixture and tests

- [x] **A · Index and ranking unit tests on a small hand-written index. A test that the generated index contains `UpgradeSpringBoot_3_4` for `spring-boot-starter-parent 3.4.x`. One tagged integration test: a Spring Boot 3.3 → 3.4 fixture (base and head commits, head = only the parent bumped) with at least one change the recipe migrates by type** — *recommended.* A minor Boot 3 upgrade is the typical Renovate PR. Fast unit tests cover the edge cases. The integration test proves the whole path, including Q7 and Q8. It needs network, like M1's.
- [ ] **B · As A, but with Spring Boot 2.7 → 3.0 (`javax` → `jakarta`)** — The hardest case and a strong test for Q8, but needs a JDK 17 fixture with many moving parts. Better suited for the benchmark (M6).
- [ ] **C · Unit tests only** — Fast, but never proves the plugin runs.

**Notes:** A

## Round 2

Triggered by the notes on Q4 and Q6.

```
old PR: bot opened "3.4.1" weeks ago        base branch meanwhile: 3.4.5
        │                                              │
        └──────────── the tool must never move 3.4.5 back to 3.4.1 ─┘
```

### Q15 · Downgrade protection

The note on Q4: an old PR must never move a dependency back from a newer version. OpenRewrite's upgrade leaves are meant to only upgrade, but I haven't checked every leaf type, and an outdated PR is a separate case.

- [x] **A · Three rules. (1) If `toVersion` is not higher than `fromVersion`, it isn't an upgrade: no recipe. (2) With `--base`: if the base already has the package at a version higher than `toVersion`, the PR is outdated: no recipe, and the report says so. (3) After the recipe, if any package resolves to a lower version than before the run, discard the recipe result like a failed run (Q11)** — *recommended.* Covers both ways a downgrade can happen: an outdated PR and a recipe that sets a version back. Verify still runs, so the report stays complete. Rule 2 needs the versions on the base commit (Q16).
- [ ] **B · Only rules 1 and 3** — No base lookup. Outdated PRs are left to the bots, which usually close superseded PRs. Doesn't help when a bot leaves an outdated PR open.
- [ ] **C · Only rule 1** — Cheapest, but trusts every recipe never to downgrade.

**Notes:** A (answered in chat)

### Q16 · How dependency versions are read

Q9 (list every version change in the report) and Q15 both need the dependency versions of a working tree. With a Spring Boot parent, most versions are not written in `pom.xml` at all. They come from the parent.

- [x] **A · New optional adapter capability: resolved versions of a working tree (`package → version`). Maven: Maven's own dependency resolution (e.g. `dependency:list`)** — *recommended.* Effective versions, including the ones managed by a parent, which is where a downgrade would hide. Works even when the code doesn't compile. The shape is ecosystem-neutral (`npm ls --json`, `pip list --format json` later), and it's what the M8 fallback (`manifestDiff`) can build on. Costs one dependency-resolution run per state (before, after, base).
- [ ] **B · Parse the declared versions in `pom.xml`** (parent, `*.version` properties, explicit versions) — No extra Maven run, but misses managed versions and property tricks.
- [ ] **C · No structured versions: the report shows the raw diff of the build files** — Least work, but Q15 rules 2 and 3 become impossible, and Q9 is only half met.

**Notes:** A (answered in chat)

### Q17 · How generic M2 is

The note on Q6: don't build it Java-shaped. Python, npm, and others must fit without changing `core`. Only Maven is implemented in M2.

- [ ] **A · Generic shapes, Maven content. `core` types and the index format carry `ecosystem` and contain no Maven terms: `package` and the recipe's artifact are opaque strings that only the ecosystem's adapter interprets. Version comparison is looked up by `ecosystem` in `recipes`, with only `maven` implemented. A change for an unknown ecosystem finds no recipe** — *recommended.* Python or npm then means new index entries, a version scheme, and an adapter, but no change to `core` or the index format. It matches the concept (core knows no language) without building a second ecosystem now.
- [x] **B · A, plus `VersionScheme` provided by the `EcosystemAdapter` now** — Reopens Q4 (C). Cleaner separation, but an interface with one implementation.
- [ ] **C · A, plus indexing OpenRewrite's Python and JavaScript recipes now** — Proves the format early, but those modules are less mature, their licenses are unchecked (concept section 9), and nothing could run them before M9.

**Notes:** B (answered in chat). Supersedes the location part of Q4: version ordering and selector matching come from the adapter, not from `recipes`
