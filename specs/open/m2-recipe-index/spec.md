# M2 – Recipe index and OpenRewrite run · Spec

Milestone: [M2 in features.md](../../../docs/features.md#m2--recipe-index-and-openrewrite-run-) · Decisions: [brainstorming.md](brainstorming.md) · Status: **Ready to implement**

## Goal

`lector migrate <repo> --package … --from … --to …` finds the right OpenRewrite recipe for a dependency update without an LLM, applies it through the Maven plugin, never downgrades anything, and then verifies the result with M1.

**Why:** the recipe does the deterministic part of a migration. Everything it fixes, the fix loop (M3) doesn't have to guess at. The index has to be derived from recipe metadata, not maintained by hand (concept section 4), and it must not be shaped around Java: Python, npm, and others must fit later without changing `core` (brainstorming Q6, Q17).

## What to build

### 1. Data model and ports in `core`, with no Maven terms

- `DependencyChange` with `ecosystem`, `package`, `fromVersion`, `toVersion`, `updateType`.
- `ecosystem` is the **package namespace** (`maven` for every JVM build, later `npm`, `pypi`, …), not the build tool.
- `package` and a recipe's artifact are **opaque strings**. Only the ecosystem's adapter interprets them.
- `RecipeIndex` port: finds the recipe for a `DependencyChange`, and returns the chosen recipe plus the alternatives.
- `EcosystemAdapter` grows by:
  - `versionScheme` (required): orders versions, decides whether a selector contains a version, and derives `updateType` for its ecosystem.
  - `recipeRunner` (optional): runs a recipe on a working tree.
  - **Resolved versions** (optional): the effective version of every package in a working tree (`package → version`).

**Why:** the core knows no language (rule 1). The change for an unknown ecosystem simply finds no recipe, so a new ecosystem means new index entries, a version scheme, and an adapter, not a change to `core`. `VersionScheme` lives in the adapter (decision Q17). It has two real users in M2: recipe matching and the downgrade rules. Resolved versions are needed by the downgrade rules and the version list in the report (Q15, Q16). Both new capabilities are optional, like in the concept, because not every ecosystem will have a recipe runner.

### 2. Recipe index, generated at build time in a new module `recipes`

- A Gradle task in `recipes` loads every recipe of the `rewrite-recipe-bom` (version in the version catalog) and writes the index as a resource of the module. The index is generated by `./gradlew build`, not committed.
- The index reads these leaves anywhere in a recipe's tree: `UpgradeDependencyVersion` (the `maven` and the `java.dependencies` variants), `UpgradeParentVersion`, `UpgradePluginVersion`. Glob artifact IDs (`*`) stay patterns.
- Selectors: exact versions and X-ranges (`3.4.x`, `3.x`). Leaves with any other selector (`latest.release`, `latest.patch`, ranges, …) are skipped and counted.
- Each entry holds: ecosystem, package pattern, selector, recipe name, leaf depth, the artifact that contains the recipe (coordinates with version), and that artifact's license.
- Next to the index, the build writes an **index report**: number of indexed recipes and leaves, skipped leaves by reason, and the license of every recipe artifact.
- At run time, the index is read from the resource. OpenRewrite is not on the runtime classpath, and building the index needs no network at run time.
- Only recipes from the official BOM. No user-provided recipes.

**Why:** build time keeps the runtime small, offline, and deterministic per tool version. A Dependabot bump of the BOM rebuilds the index by itself, so nothing can go stale (Q1). The three leaf types cover what Renovate and Dependabot bump in a Maven project (Q3). `latest.*` selectors are unbounded and would always overshoot (Q4). The artifact coordinates tell the runner what to fetch. The license per artifact matters because `rewrite-spring` is under the Moderne Source Available License (Q2).

### 3. Recipe selection

- A recipe's target for a package is its **highest** matching leaf for that package across the whole tree. So `UpgradeSpringBoot_3_4`, which includes the 3.3 recipe, never matches a change to 3.3.
- A recipe matches when that target's selector contains `toVersion` (decided by the adapter's `versionScheme`).
- Ranking: tightest selector first (`3.4.x` beats `3.x`), then shallowest leaf (direct child beats nested), then recipe name.
- The chosen recipe and all other matches are logged and reported.
- No LLM, no embedding search.

**Why:** deterministic and explainable (rule 2, Q5). The shallowest-leaf rule prefers the recipe that is *about* the package over one that only includes it.

### 4. Downgrade protection

Three rules. None of them changes the exit code. Verify always runs.

1. **Not an upgrade:** if `toVersion` is not higher than `fromVersion`, no recipe runs. Reported.
2. **Outdated PR:** with `--base`, if the base commit already resolves the package to a version higher than `toVersion`, no recipe runs. Reported as "PR outdated", with both versions.
3. **Recipe downgrade:** if any package resolves to a lower version after the recipe than before it, the recipe result is discarded like a failed run (section 6). Reported with the affected packages.

If the versions needed for rule 2 or 3 can't be read (e.g. dependency resolution fails), no recipe runs, or its result is discarded. Reported.

The base versions (rule 2) are read in a separate worktree, like M1's baseline run, and the worktree is removed afterwards.

**Why:** an old PR must never move a dependency back from a newer version (note on Q4, decision Q15). The rules cover both ways it can happen: an outdated PR, and a recipe that sets a version back. When the versions can't be read, the tool can't prove that nothing went down, so it doesn't apply the recipe.

### 5. Maven: version scheme, resolved versions, recipe runner in `ecosystems:jvm`

- **Version scheme:** Maven ordering via `ComparableVersion` from `maven-artifact` (`3.2.0-RC1 < 3.2.0`). Exact versions and X-ranges as selectors.
- **Resolved versions:** from Maven's own resolution, so versions managed by a parent are included. They cover dependencies, parents, and plugins, the three kinds the index reads. This has to work when the code doesn't compile. (`dependency:list` alone doesn't list parents or plugins.)
- **Recipe runner:** `rewrite-maven-plugin` called by coordinates with the goal **`runNoFork`**. Batch mode, `--maven-settings` passed through, `./mvnw` or `mvn` as in M1. Recipe artifact and recipe name come from the index entry. The plugin version is pinned in the version catalog.
- No file of the target repository is edited to run the recipe. The recipe's own changes are the only changes.
- The recipe runs on the PR head as it is (Q8).

**Why:** the user's Maven fetches the recipe artifacts like any other dependency, so recipe JARs are never shipped with the tool (Q2), and regulated environments use their configured mirror (M1 Q11). `runNoFork` avoids the forked lifecycle that would compile the project first, and compiling fails exactly when the update broke it (Q7). The "head as is" choice is a known risk: types that no longer exist on the new classpath may stop type-based recipe steps from matching. The fixture checks it (section 8).

### 6. Working tree and recipe failures

- `migrate` requires a clean working tree. If it isn't clean, it exits with `2` before doing anything.
- The recipe runs in place. Its changes (modified and new files) are captured with Git and stay uncommitted.
- A recipe run that fails, or that rule 3 rejects, counts as "no recipe": the working tree is reset to its state before the run, the reason is reported, and verify continues.
- A successful run is kept, including version changes beyond the PR. Every version change (before vs. after, from resolved versions) is listed in the report, including the PR's own package if the recipe moved it to a newer patch.

**Why:** a clean start means a reset can never destroy someone's work. Git capture is language-neutral, and the diff becomes the recipe commit in M5 (Q10). The recipe is a quality boost, not a prerequisite (concept section 4, Q11). Framework recipes are meant to move managed dependencies too. The reviewer sees every change instead of the tool silently reverting some (Q9).

### 7. CLI command `migrate`

- `lector migrate <repo> --package <package> --from <version> --to <version> [--base <git-ref>] [--format text|json] [--maven-settings <file>]`
- `ecosystem` comes from the detected adapter. `updateType` is computed by the adapter's version scheme. One change per run.
- Flow: build the change → downgrade rules 1 and 2 → find recipe → read versions → run recipe → rule 3 → verify (M1) → report.
- The report has a **recipe section** before the M1 verification: chosen recipe and its artifact, alternatives, changed files, version changes. If no recipe ran, the section says why: no match, not an upgrade, PR outdated, run failed, downgrade detected, versions unreadable, or no recipe runner for this ecosystem.
- `--format json` contains the same recipe section plus the `Verification`.
- Exit codes as in M1: `0` / `1` from the verification. `2` for a tool error: unsupported repository, dirty working tree, invalid base ref, missing or invalid options. A skipped or failed recipe is not a tool error.
- `verify` is unchanged.

**Why:** each command maps to one pipeline stage, and `heal` (M3) adds the fix loop on top (Q13). Explicit options are easy in tests and stay useful for the benchmark (Q12). The recipe is optional, so its outcome never decides the exit code.

### 8. Tests and fixtures

- **Index and ranking unit tests** on a small hand-written index: highest-leaf target, no overshoot, X-range matching, tightest selector, shallowest leaf, name order, unknown ecosystem.
- **Downgrade unit tests** with a fake adapter: one per rule, plus unreadable versions.
- **Maven version scheme unit tests:** ordering with qualifiers, X-range containment, `updateType`.
- **Generated index test:** the real index contains `org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_4` for `org.springframework.boot:spring-boot-starter-parent` with selector `3.4.x`, and the index report lists the license of `rewrite-spring`.
- **One tagged integration test** with real Maven: a Spring Boot 3.3 → 3.4 fixture with a base commit and a head commit. The head only bumps the parent, like a bot PR. The fixture contains at least one change that the recipe migrates by type (picked from the recipe's documented steps). The test checks that `UpgradeSpringBoot_3_4` is chosen, applied, that the type-based change happened, and that verify ran.

**Why:** fast unit tests cover the edge cases. The integration test proves the whole path: index, runner, `runNoFork`, version reading, verify. The type-based change is the tripwire for decision Q8. If it is missed, Q8 is reopened, not worked around.

## What not to do

| Don't | Why |
|---|---|
| Commit the generated index | Decided against (Q1): generated by the build so it can't go stale. |
| Load OpenRewrite or recipe JARs at run time, or use `rewrite:discover` | Decided against (Q1): the runtime stays small, offline for the index, and deterministic. |
| Support user-provided or internal recipes | Not needed (Q1 answer). |
| Ship recipe JARs in the distribution | The user's Maven fetches them (Q2). This keeps the MSAL question manageable until the legal check. |
| Filter to Apache-only modules or add a license opt-in flag | Decided against (Q2). The license is recorded and reported instead. |
| Index `ChangeDependency`, `ChangeParentPom`, or other leaf types | Decided against (Q3). |
| Interpret `latest.*`, tilde, caret, or range selectors | Decided against (Q4): skipped and counted. |
| Put version ordering or selector logic in `recipes` or `core` | It comes from the adapter's `versionScheme` (Q17). |
| Use Maven terms (`groupId`, `artifactId`, `pom`) in `core` types or the index format's field names | Q6, Q17: the shapes stay generic for Python, npm, and others. |
| Index Python, JavaScript, or other non-JVM recipes | Q17: less mature, licenses unchecked, nothing can run them before M9. |
| Run OpenRewrite in-process or through the Moderne CLI | Decided against (Q7). |
| Use the `run` goal, or add the plugin to `pom.xml` | `runNoFork` by CLI coordinates only (Q7, concept section 5). |
| Reset manifests to the base, or run the recipe on a base worktree | Decided against for now (Q8). Reopen only if the fixture shows the problem. |
| Reject or revert version changes beyond the PR | Decided against (Q9): accepted and reported. Downgrades are the only exception (Q15). |
| Commit the recipe result, or use `dryRun` and a patch file | Decided against (Q10). Commits are M5. |
| Verify twice to compare with and without the recipe | Decided against (Q11). |
| Fail the run, or exit `2`, because the recipe failed or was skipped | Decided against (Q11): the recipe is optional. |
| Detect the change from the Git diff, read it from a JSON file, or accept several changes | Decided against (Q12). Diff detection is the M8 fallback, grouped changes come with source adapters. |
| Add `manifestDiff` | M8. Resolved versions are the building block it can use later. |
| Add a `recipes find` command or a combined `run` command | Decided against (Q13). |
| Add embedding search over recipe names | Concept "Later". |
| Call an LLM | Rule 2: recipe selection is deterministic. |
| Support Gradle, source adapters, or Git output | M7, M5. |

## Acceptance criteria

The review agent checks every criterion and reports it as *met*, *not met*, or *can't verify*, with evidence.

| AC3 | `core` sources contain no Maven terms | 1, Don't | Case-insensitive search of `core/src/main` for `maven`, `groupId`, `artifactId`, `pom`: no matches |
